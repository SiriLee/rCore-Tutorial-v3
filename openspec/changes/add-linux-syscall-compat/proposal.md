## Why

rCore 的用户程序均面向裸机目标编译，使用专用链接脚本与自定义调用约定，因此无法运行生态中已有的 Linux 程序。实测一个最小的静态 Linux 程序需要 24 种系统调用，rCore 仅 4 种语义可用；且遇到未实现的调用编号时内核直接 panic，导致整个系统崩溃。可行性验证（`project/docs/feasibility.md`）已定位三个拦路问题：装载位置假设页对齐、启动参数布局不同、系统调用可用率过低且失败方式不可接受。

## What Changes

- 程序装载：按可执行文件的段偏移信息放置各段，不再假设段起始地址页对齐。
- 进程启动：按 Linux 约定构造启动栈（参数个数、参数、环境变量、辅助向量），使静态标准库能够启动。
- 系统调用入口：参数由 3 个扩展为 6 个。
- 新增 Linux 兼容层：调用号翻译、错误码约定，并补齐缺失的系统调用。
- 进程级调用约定标记：使 rCore 既有用户程序与 Linux 程序共存，既有程序无需迁移。
- 未实现的调用返回 `-ENOSYS`，不再导致内核崩溃。
- 文件系统接口：补充文件大小与类型查询，供 `fstat` 一类调用使用。

## Capabilities

### New Capabilities

- `linux-syscall-compat`: 内核按 Linux 约定装载程序、构造启动参数并处理系统调用的能力，包含未实现调用的降级行为。

### Modified Capabilities

（无：既有能力的行为不变，本次只新增能力。）

## Impact

- 代码：`os/src/mm`、`os/src/task`、`os/src/trap`、`os/src/syscall`、`os/src/fs`，以及 `easy-fs` 的 `Inode` 接口。
- 行为：rCore 既有用户程序的调用路径必须保持不变；这是回归验收的前提。
- 依赖：新增 Linux 侧测试程序的交叉编译流程（静态 musl），不改变内核构建依赖。
