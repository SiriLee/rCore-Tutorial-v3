## Context

动机见 `proposal.md` 的 Why 一节。当前内核的用户程序面向 `riscv64gc-unknown-none-elf` 编译，使用 `user/src/linker.ld` 与自定义调用约定；可行性验证（`project/docs/feasibility.md`）已定位三个拦路问题，并确认用现有工具链即可产出 Linux 程序的交叉编译流程。

## Goals / Non-Goals

**Goals:**

- 让未经修改的 RISC-V Linux 静态程序在 rCore 上运行到 `main`，并能进行文件与内存操作。
- 保证 rCore 既有用户程序与自测用例的行为不变。

**Non-Goals:**

- 不支持动态链接程序：内核没有动态加载器。
- 不实现进程级当前工作目录：验收限定为绝对路径。
- 不实现删除文件与创建目录：文件系统不具备该能力。
- 不追求覆盖 Linux 的全部系统调用，只覆盖基准集合与 busybox 所需子集。

## Decisions

### 决策一：用进程级调用约定标记，而不是迁移既有程序

部分调用号在两套约定下语义冲突（例如 56 号），仅凭编号无法判别语义，因此为进程增加标记并在系统调用入口分派。

- 备选方案：把既有的 59 个用户程序全部迁移到 Linux 约定。放弃原因：改动面大，回归风险高。

### 决策二：装载时按段偏移写入，而不是要求链接脚本页对齐

按可执行文件的规范处理段起始地址的页内偏移，使内核能够装载任意符合规范的 Linux 程序。

- 备选方案：用自定义链接脚本重新编译 Linux 程序以规避该问题。放弃原因：违背"运行未经修改的程序"这一目标。

### 决策三：未实现的调用返回 `-ENOSYS`

把缺失调用的影响限制在单个进程内，使补齐调用可以逐条进行。

- 备选方案：保持当前 panic 行为。放弃原因：每次缺失都导致内核崩溃，开发过程无法迭代。

### 决策四：文件系统只补最小可用的元数据查询

`fstat` 需要文件大小与类型，而现有 `Inode` 未暴露。只补这两项查询，不引入完整的元数据模型。

## Risks / Trade-offs

- [真实程序依赖的调用集合会持续增长，验收边界漂移] → 在规格中固定验收对象为 `min_raw`、`min_std` 与 busybox 的 `echo`/`cat`/`ls`。
- [兼容层改动可能影响既有程序的调用路径] → 分派点集中在系统调用入口，既有路径保持不变，并以既有用例逐项对比回归。
- [文件系统缺少目录项类型信息] → `ls` 允许只输出名称，类型信息按需补充。
- [glibc 版 busybox 启动要求高于 musl 版] → 优先采用 musl 版本。
