# 可行性验证报告：让 rCore 运行 Linux 程序

> **内部技术文档**：记录实测过程与结论，供组内开发使用，**不作为提案正文提交**。提案正文见 `docs/proposal.md`。
> 配套证据：`evidence/`（运行日志）、`programs/`（测试程序源码）、`build/`（编译产物，由脚本生成）。

- 验证日期：2026-10-07
- rCore 基线：`rCore-Tutorial-v3`，分支 `lab-2`，HEAD `ece51179`（其中 `os/` 目录与 `oslab-2026-base` 完全一致）
- 宿主环境：WSL2 / Ubuntu 24.04 / x86_64；rustc 1.98.1；QEMU 8.2.2
- 新增工具链：`rustup target add riscv64gc-unknown-linux-musl`（未安装 apt 包，未使用容器）

## 摘要

**结论：可行。** 三个拦路问题已全部定位。

| # | 现象 | 原因 | 影响 |
| --- | --- | --- | --- |
| 1 | 程序装入后立即报「非法指令」 | 内核假设每个程序段都从页边界开始，而 Linux 程序不保证这一点 | 当前无法启动的直接原因 |
| 2 | 标准库程序无法启动 | 启动参数的摆放方式与 Linux 约定不同 | 即使问题 1 修好也跑不起来 |
| 3 | 一发起系统调用就崩 | 24 种调用只有 4 种可用；未实现的调用直接让内核崩溃 | 必须补齐调用，并改造出错方式 |

**已经验证的两件事**：

1. 用现有 Rust 工具链就能产出真正的 Linux 程序，最小程序只有 **1920 字节**；
2. rCore 能装入该程序并开始执行——**路径是通的，只是卡在上面三个问题上**。

## 1. 验证目标与方法

目标：确认「让 rCore 直接运行 Linux 程序」这条路是否走得通，并找出拦路的具体是什么。

方法：

1. 用 Rust 交叉编译两个 Linux 程序：`min_raw`（只用两个系统调用，尽可能小）与 `min_std`（带标准库，代表普通程序）；
2. 把程序打进 rCore 的文件系统镜像；
3. 在 QEMU 中启动 rCore，从它的命令行运行这两个程序，观察结果。

## 2. 验证结果

### 2.1 能造出 Linux 程序

用现有工具链交叉编译，得到标准的 RISC-V Linux 静态程序。最小程序只有 1920 字节，全部代码仅 10 条指令：先调用 `write` 打印一行字，再调用 `exit` 退出（反汇编见附录 B.1）。

带标准库的 `min_std` 为 6.9 MB，含 4 个程序段。由此得到两条约束：**必须静态链接**（rCore 没有动态加载器），且**优先选 musl 版本**（体积更小、启动要求更低）。

编译过程中有两个坑：默认链接器是宿主的 x86_64 链接器，必须改用 Rust 自带的 `rust-lld`；`-nostartfiles` 是 gcc 的参数，不能传给 lld。

### 2.2 能装进 rCore，但立刻失败

程序被成功装入并进入用户态执行，随即触发非法指令：

```
Rust user shell
>> min_raw
[kernel] Illegal Instruction, SIGILL=4
```

这说明**装载和跳转本身没有问题，问题出在装入的位置**。

## 3. 三个拦路问题

### 3.1 程序装载位置错误（当前失败的直接原因）

Linux 程序文件有一条约定：各段在文件中的偏移，与它在内存中的地址，只需「除以 4096 后余数相同」，**并不要求从页边界开始**。`min_raw` 的执行段正是这种情况——起点地址的页内偏移是 0x200。

而 rCore 的装载代码按「段从页边界开始」的假设工作，把段内容直接从页首写入。结果整段代码向前错位了 512 字节，程序入口处变成一片空白；CPU 读到空白，报非法指令。

rCore 自带的 59 个用户程序使用它自己的链接脚本，恰好满足页对齐，所以这个假设从未暴露。**与其说这是 rCore 的 bug，不如说它的装载器只覆盖了自己产生的那一类程序文件。**

### 3.2 启动参数摆放方式不同

Linux 的约定是：程序启动时，参数（程序名、命令行参数、环境变量等）按固定格式摆在栈顶，由程序自己从栈顶读取。musl 的启动代码正是这么做的——它一上来就把**栈顶的整数**当作「参数个数」。

而 rCore 不往栈上写这个整数，改用寄存器传递，也没有环境变量等后续内容。因此任何标准库程序启动时都会读到错误的数据。**即使 3.1 修好，这一条不修也跑不起来。**

### 3.3 系统调用只有 4/24 可用

以 `min_std` 实际用到的调用为基准（共 24 种），rCore 只有 4 种语义可以直接对应，其余 20 种缺失或含义冲突。例如：

- 编号 56 在 rCore 是「打开文件」，在 Linux 是「在指定目录下打开文件」，参数个数不同；
- 编号 23 在 Linux 是 `dup`，而 rCore 把 `dup` 放在了编号 24。

更严重的是**出错方式**：内核遇到未实现的调用编号时执行 `panic!`，导致整个内核崩溃，而不是让该程序收到一个错误。完整对照表见**附录 A**。

## 4. 实现工作量清单

| 模块 | 改动 | 对应问题 |

| 进程启动 | 按 Linux 约定摆放启动参数（参数个数、参数、环境变量等） | 3.2 |
| 系统调用入口 | 参数由 3 个扩展到 6 个 | 3.3 |

## 5. 已知缺口与需确认项（开工前必读）

以下是提案阶段尚未覆盖、但直接影响 G3 / G4 的问题：

1. **内核没有「当前工作目录」概念**：全仓库检索 `cwd` / `AT_FDCWD` 为空，路径一律从根目录解析。而 Linux 程序大量使用相对路径，`busybox ls` 不带参数时列的是 `.`。处理方式二选一：新增进程级工作目录，或把验收限定为绝对路径（**提案目前采用后者，验收命令为 `busybox ls /`**）。
2. **文件系统缺少元数据接口**：easy-fs 的 `Inode` 只有 `find` / `create` / `ls` / `read_at` / `write_at` / `clear`，没有文件大小与类型查询，而 `fstat` 需要它们。
3. **没有删除与建目录能力**：因此创建目录、删除文件一类命令不在验收范围内。
4. **错误码约定不一致**：rCore 的 `sys_open` 等失败时返回 `-1`，Linux 要求返回 `-errno`，兼容层需统一翻译。
5. **libc 选择影响难度**：Debian 的 `busybox-static` 基于 glibc，启动要求高于 musl；Alpine 的 busybox 是 musl 版，与现有测试程序一致。实现 G4 时优先用 musl 版本，可减少所需调用。

## 6. 推进阶段与分工

目标表以提案正文为准（`docs/proposal.md` 第 2.2 节）。推进阶段：

- **第一阶段（中期检查点）**：G1 + G2 完成——最小 Linux 程序可启动，未实现的调用不再使内核崩溃。这是判断方向是否继续的依据。
- **第二阶段**：G3 完成——标准库程序可运行。
- **第三阶段（冲刺）**：G4——busybox 命令。若时间不足，降级为「跑通 2 个命令」。

分工：

- **甲（关键路径）**：G1 + G2——装载、启动参数、入口参数扩展、调用约定分流。**必须最先完成。**
- **乙**：系统调用兼容层实现（文件、内存、进程与运行环境）+ 交叉编译、镜像注入与回归对比脚本。
- **共同**：G4 的联调与答辩材料。

风险：最大风险是**范围失控**——真实程序依赖的调用会不断增长，必须固定验收对象（提案中固定为 busybox 的 `echo`、`cat`、`ls /` 三个命令）。

## 附录 B：关键证据

### B.1 最小程序的反汇编（全文）

```asm
0000000000011200 <_start>:
   11200: auipc a1, 0xfffff
   11204: li    a7, 0x40        # 64 = write
   11208: li    a0, 0x1         # fd = stdout
   1120a: addi  a1, a1, -0x70   # buf
   1120e: li    a2, 0x2a        # len = 42
   11212: ecall
   11216: li    a7, 0x5d        # 93 = exit
   1121a: li    a0, 0x0
   1121c: ecall
```

`a7` 传调用号、`a0`–`a2` 传参数，正是标准 Linux 约定；而 rCore 的入口虽然也取这三个参数，却只用它们，且调用号另有语义。

### B.2 程序的段布局（`min_raw`）

| 段 | 文件偏移 | 内存地址 | 页内偏移 |
| --- | --- | --- | --- |
| LOAD 1 | `0x000` | `0x10000` | 0 |
| LOAD 2（执行段） | `0x200` | `0x11200` | **0x200** |

Linux 只要求「文件偏移与内存地址除以 4096 的余数相同」，并不要求余数为 0；而 rCore 的装载代码按余数为 0 处理。
